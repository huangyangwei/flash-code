## Context

当前两个项目的运行时边界不同：`flash-code` 是 `net8.0-windows` WinForms 程序，拥有 Windows 屏幕抓取、Windows/Paddle OCR、Win32 剪贴板、全局热键和 SendInput；`flash-video` 是 Vite 前端，使用 `mpegts.js` 播放 FLV，并把抖音房间页轮询挂在 Vite 开发服务器插件上。浏览器直接轮询抖音房间页会受到 CORS 限制，当前自动监测因此依赖 Node 侧。

合并目标是一个 Windows 客户端，而不是让两个进程互相调用。现有 OCR 抓取仍是屏幕区域模型，所以视频必须保持可见；现有 FLV 地址带签名且会过期，监测和播放器必须保留手动地址兜底。设计要求详见本变更下的四份 capability spec。

## Goals / Non-Goals

**Goals:**

- 以现有 WinForms 程序作为 Windows 生命周期、托盘、热键、配置和原生能力宿主。
- 在宿主窗口中承载现有 Web 播放器，并通过明确的双向消息协议连接播放、监测和 OCR 状态。
- 将房间页轮询与解析迁移到宿主，去掉最终运行时对 Vite 开发服务器和 Node.js 的依赖。
- 保留现有低延迟播放策略、OCR 低延迟预算、剪贴板 fail-safe 清空和自动粘贴边界。
- 让前端构建产物可随桌面程序发布，并支持从旧的独立工具逐步迁移。

**Non-Goals:**

- 不重写 FLV/MSE 播放内核，不自行实现视频解码器或替换现有追帧算法。
- 不把 OCR 改成直接解析直播流帧；第一版继续要求选定画面可见并使用屏幕区域抓取。
- 不做多房间调度、代理池、签名生成、风控绕过或多用户服务。
- 不在本变更中删除或强制废弃两个旧项目；它们作为回滚和对照运行路径保留到合并验收完成。

## Decisions

### 1. 使用现有 WinForms 程序作为宿主，嵌入 Web 播放 UI

在 `RoomCodeGrabber` 中增加 WebView2 容器，把 `flash-video` 的构建产物作为应用资源加载。这样能直接复用 `mpegts.js`、MSE、浏览器媒体兼容性和现有前端 UI，同时让 OCR、剪贴板、托盘和全局热键继续使用已经验证过的 Windows 实现。

备选方案是把播放器改写为原生 FFmpeg/libVLC 控件，或者把 OCR 做成 Electron/Tauri 插件。前者会重写低延迟缓冲和追帧逻辑，后者会引入另一套原生桥和打包体系，均会扩大风险面。

### 2. 运行时由 C# 宿主负责房间监测

将 `flash-video/src/lib/room-page.js`、`watch-decision.js`、`watch-engine.js` 的可观察行为迁移为 C# 服务：使用带浏览器 User-Agent/Referer 的 HTTP 请求获取房间页，解析直播状态和 FLV 地址，保留冷启动触发、跳变沿、失败退避、硬超时和停止令牌。

监测服务的状态快照只包含房间、间隔、是否直播、地址是否存在、最近检查时间、错误和失败次数；Cookie 只在宿主请求层保存和使用，不放入日志或回传给前端。解析器必须将验证页、字段缺失和明确下播区分开，不能用不完整页面误报开播。

保留 JavaScript 版纯逻辑测试夹具作为行为对照，新增 C# 版单元测试覆盖归一化、解析、跳变沿和退避。这样迁移改变实现语言，但不改变 monitor spec 的外部行为。

### 3. 使用显式 JSON 消息协议连接宿主与播放 UI

WebView2 与宿主通过 JSON 消息通信，不直接暴露任意 .NET 对象给页面。协议按事件和命令分层：

| 方向 | 消息 | 作用 |
| --- | --- | --- |
| Host -> UI | `app.init` | 下发非敏感配置、默认值和能力状态 |
| Host -> UI | `monitor.status` | 下发监测状态和可展示错误（不含 Cookie） |
| Host -> UI | `monitor.stream` | 下发新鲜 FLV 地址并标记来源为自动监测 |
| Host -> UI | `capture.status` / `capture.code` | 下发 OCR 状态、识别码和延迟 |
| UI -> Host | `monitor.start` / `monitor.stop` | 请求启动或停止房间监测 |
| UI -> Host | `playback.manual-start` | 请求播放用户粘贴的地址 |
| UI -> Host | `playback.settings` | 保存并应用追帧设置 |
| UI -> Host | `capture.select` / `capture.toggle` | 请求框选、开始或停止 OCR |
| 双向 | `app.error` | 关联操作的可读失败信息和恢复动作 |

消息处理必须校验类型、字段和范围；未知消息被拒绝并记录非敏感错误。宿主生成的 `monitor.stream` 复用前端的同一播放入口，不创建第二套自动播放路径。

备选方案是保留本地 HTTP `/__watch/api`。它能减少初期迁移工作，但仍保留一个后台服务器边界和端口生命周期，不符合单客户端交付目标。

### 4. 配置由宿主统一持久化，前端只做视图状态

扩展现有 `AppConfig`，为监测房间/间隔、播放追帧设置和前端 UI 偏好提供统一字段。每次 UI 修改经消息提交，宿主校验、保存并回传实际生效值；前端不再把 Cookie 或核心设置独立写入 `localStorage`。旧配置缺少新增字段时使用当前项目默认值。

Cookie 等凭据在磁盘上使用 Windows 保护机制保存，状态展示只返回布尔值。配置损坏时逐字段回退，不能阻止客户端启动。播放 URL 属于短期敏感运行数据，不写入持久化配置，除非用户明确选择保存。

### 5. OCR 继续抓取可见的合成画面

第一版复用 `CaptureEngine`、`RegionSelector`、`CodeDetector`、`ClipboardService` 和 `AutoPasteScheduler`。框选坐标仍以屏幕像素保存，视频播放区域需要保持可见；识别到新码时由宿主更新前端状态并执行原生剪贴板/自动粘贴。

不在第一版切换为 DOM/canvas 帧读取：这会受到跨源媒体、硬件解码和浏览器安全策略影响，也会破坏 OCR 对外部窗口的通用能力。必须增加一条真实 WebView2 硬件合成验证；若某些 GPU/全屏模式无法被 `CopyFromScreen` 捕获，客户端应明确提示用户改用可见窗口模式，而不是发出猜测的房间码。

### 6. 前端资源以构建时输入、嵌入式资源发布

在合并后的源码树中保留一个前端子目录，构建时运行现代 Node/Vite 生成静态资源，发布时将 `dist` 放入宿主资源。生产客户端不启动 Vite 插件，也不依赖 Node 版本。开发环境仍可单独运行前端，便于迭代播放器 UI，但自动监测的最终验收必须走宿主服务。

### 7. 客户端界面继承现有工具语汇，扩展为播放器优先的工作台

设计上下文（2026-09-18）：模式为 extend；依据是 `flash-video/index.html`、`src/main.js` 的播放器、监测、追帧和断流操作，以及 `RoomCodeGrabber/MainForm.cs` 的抓码、剪贴板、热键和 OCR 设置。两个现有界面都没有设计 token 或组件库，页面当前是未装饰的原生控件，所以不保留其旧布局作为视觉规范。

将视频作为主区域，监测/抓码作为相邻的持续操作面板，设置放在收起的次级区域。深色中性底色降低观看时干扰，青绿色表示有效运行，暖黄色表示等待，红色表示错误；状态不只依赖颜色。保留现有控件名称和行为，复用前端的 `video`、URL 输入、追帧输入及错误弹窗，加入明确的空载、加载、直播、失败和 OCR 成功状态。验收时检查 1440x900、1024x768、390x844 的布局、键盘聚焦、错误恢复、长 URL 换行/截断和控制可触达性；这套 UI 不作为营销首页。

## Risks / Trade-offs

- [WebView2 硬件合成画面无法稳定被 GDI 屏幕抓取] -> 在首个垂直切片加入真实 WebView2 播放 + OCR smoke 测试；保留可见窗口和手动区域选择提示，不静默输出错误码。
- [WebView2 Runtime 缺失或版本差异] -> 发布安装器检查并引导安装 Evergreen Runtime；启动时展示明确依赖错误，并保留独立 `flash-code` 回滚路径。
- [抖音房间页私有字段改版或触发验证码] -> 解析失败宁可不触发；保留失败原因、指数退避和手动 FLV 输入；解析器使用夹具测试而不假设页面永不变化。
- [FLV 签名过期或 CDN 不允许嵌入式请求] -> 播放器保留替换地址和初始连接有限重试；监测到新地址后允许热更新播放。
- [消息协议字段漂移造成 UI/宿主状态不一致] -> 版本化消息 envelope，所有消息做字段校验，加入宿主假 WebView 和前端协议测试。
- [前端与宿主各自保存设置导致覆盖] -> 宿主是唯一持久化源，UI 只显示宿主确认后的值；迁移期间对旧 `localStorage` 做一次性读取后不再写入敏感字段。
- [Node 14 等旧环境误报构建成功] -> 将前端构建最低版本固定为 Node 20.19+，CI/发布前显式检查版本并把构建错误作为失败处理。

## Migration Plan

1. 在现有 `flash-code` 解决方案中加入 WebView2 宿主壳和前端资源加载，只实现手动 FLV 播放与现有 OCR 状态展示；旧 `MainForm` 控件和独立 `flash-video` 仍可运行。
2. 迁移播放器 UI 与追帧设置，建立消息 envelope、配置同步和协议单测；确认手动播放、断流替换和 OCR 框选在同一窗口内可用。
3. 迁移房间页解析和监测服务，接入 `monitor.stream` 自动播放，加入验证页、退避、停止和新地址刷新测试。
4. 加入 WebView2 合成画面 OCR、剪贴板和自动粘贴的真实 Windows 验收，完善安装包与 WebView2 Runtime 检查。
5. 验收通过后，将统一客户端设为推荐入口；旧项目目录保留一段时间作为回滚方案。回滚只需停用统一宿主发布物并继续使用原有 WinForms 与 Vite/CLI 流程，不需要数据迁移。
